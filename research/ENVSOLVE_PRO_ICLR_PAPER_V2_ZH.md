# EnvSolve-Pro：把终局部署失败变成 Session 内反例

## 摘要

项目部署通常被当成自由命令生成：Agent 阅读仓库、修改环境，最后输出一段部署程序。但这个视角
遮蔽了真正的困难。决定成功的兼容状态只能被部分观测，每次操作都会改变它，而且 Agent 累积构建
出来的环境可能与评测使用的全新目标环境不同。因此，即使 Agent 在交互中取得了大量局部进展，
它仍可能提交一个直到 session 结束后才暴露错误的程序。

本文将项目部署形式化为**部分可观测的状态化约束求解**，并提出“观测--约束--操作”（OCO）因果
框架，用于定位部署轨迹中最早产生决定性影响的失败。OCO 描述的是推理过程，并不要求 harness 在
模型外维护符号化约束集合。在此基础上，我们提出 EnvSolve-Pro 的最小实现：当同一个 Agent session
仍然活跃时，从目标初始状态执行它提交的完整程序；若执行失败，就把反例返回这个 session；只有
通过重放的同一份程序才能被交付。

现有开发实验表明，目标态重放能够忠实暴露原本只会在终局出现的错误，并触发同 session 修复。
实验也得到一个重要的负结果：更精细的模型外 compatibility frontier 虽然提高了诊断分辨率，却
没有在三组受控配对中提高 Official Pass@1。这些证据把环境部署研究中经常混在一起的三个量分开：
诊断是否准确、Agent 能否选出修复动作，以及最终是否部署成功。

## 1. 引言

复现一个软件仓库，远不只是预测一条安装命令。部署者需要发现什么样的解释器、依赖组合、构建
工具、生成文件、环境变量和执行顺序共同满足目标条件。许多事实只有真正执行命令后才会出现；而
每一次命令又可能切换解释器、替换二进制依赖或改变 shell 状态，从而破坏之前已经满足的条件。

强 coding Agent 很适合做这种开放式搜索。它能阅读源码、理解报错，也能提出固定包求解器无法
枚举的修复方案。但“交互环境里能跑”不等于“交付程序可复现”。例如，Agent 在探索时手工安装了
一个构建依赖，最终程序却漏掉这一步；或者程序换了工作目录、把包装进了另一个解释器。全新的
评测环境随后失败，而 Agent 已经无法继续响应。此时问题不只是少了一条报错，而是决定性报错出现
在修复闭环之外。

我们认为，更准确的定义是**部分可观测的状态化约束求解**。真实环境中存在决定兼容性的状态，
Agent 却只能看到局部观测。成功所需的条件会在执行中逐渐暴露，并且必须在环境变化后继续成立；
如何满足这些条件，仍由 Agent 自由决定。

这个定义引出两个相互独立的贡献。第一，OCO 为不同部署范式提供统一的因果语言：观测失败表示
关键的目标态事实没有在方法仍可行动时出现；约束失败表示已有证据没有被正确保留、解释或协调为
要求；操作失败表示相关要求已经明确，但状态变换或交付程序没有满足它。这些标签解释轨迹为什么
失败，与系统采用自由试错、硬规则、软反馈还是重放机制是两回事。

第二，EnvSolve-Pro 在不替代 Agent 推理的前提下闭合一个具体反馈缺口：完整部署程序在 session
结束前从目标初始状态执行；反例返回同一个 session，Agent 可以修改后重新提交；通过重放和最终
交付的是同一份程序。Harness 不枚举兼容条件，也不替 Agent 选择下一个包或命令。

本文当前有三项贡献：

1. **问题定义与因果失败框架。** 我们形式化隐藏且不断变化的兼容状态，并提出带轨迹证据的 OCO
   归因方法，用同一套语言分析不同部署范式。
2. **最小部署干预。** EnvSolve-Pro 在提出程序的 Agent session 内，把完整交付物的目标态执行
   失败转化为可执行反例，同时保留模型对环境操作的决定权。
3. **受控设计实验。** 开发期实验同时说明了可执行反馈的能力边界：目标态反例可以触发有效修复，
   但更细的残余诊断并不会自动转化为终局成功。

## 2. 问题定义

### 2.1 部署任务

一个任务写成

\[
x = (r, e_0, V),
\]

其中 \(r\) 是固定 revision 的代码仓库，\(e_0\) 是目标初始环境，\(V\) 是可执行评测器。部署
方法输出自包含程序 \(p\)，Official 成功定义为

\[
Y(p, x) = \mathbf{1}\{V(\operatorname{Exec}(e_0, p), r) = \text{pass}\}.
\]

主要指标是 case 级 Official Pass@1。时间、模型请求数、Token、网络流量和存储是次要指标，只有
在不牺牲成功率时才用于比较路径质量，不能把一次失败重新解释成成功。

### 2.2 隐藏且状态化的兼容条件

用 \(s_t\) 表示第 \(t\) 步之后的真实环境状态，包括文件系统、进程、解释器、包、构建与 shell
状态。Agent 无法直接看到 \(s_t\)，只能得到局部观测

\[
o_t \sim \Omega(s_t, a_{t-1}),
\]

例如命令输出、导入错误、包元数据或重放失败。Agent 根据历史形成内部判断

\[
b_t = B(o_{1:t}, a_{1:t-1}),
\]

再选择操作 \(a_t \sim \pi(b_t, o_{1:t})\)，使环境变为 \(s_{t+1}=T(s_t,a_t)\)。

对任意状态，都客观存在一组最终成功必须满足的兼容条件 \(C^*(s_t)\)。我们不假设它可以被完整
枚举，也不假设 harness 会把它显式存下来。它可能包括解释器一致性、构建期依赖、二进制兼容、
生成源码是否存在，以及 shell 效果能否被最终程序复现。所谓部分可观测，是指每一步只能看到这些
条件中由当前动作触发的一小部分。

问题之所以具有状态性，是因为观测有明确的时空作用域：一个包在某个解释器中可导入，不代表它
在另一个解释器中也存在；累积构建环境里的成功，不代表从零执行 \(p\) 能产生相同状态；后续安装
也可能破坏之前已经兼容的组合。

### 2.3 OCO 因果分析框架

对于一条失败轨迹，OCO 只标注一个最早的决定性原因：

- **观测层：** 成功决策所需的事实没有出现、没有被观察到，或直到方法无法继续行动后才返回。
- **约束层：** 事实已经出现，但方法错误地形成、保留或协调了要求。错误的硬规则拒绝也属于约束
  失败。
- **操作层：** 相关要求已经明确，但所选状态变换、执行顺序或最终程序没有满足它。

后续因素可以作为次要原因记录，但不能覆盖最早的决定性归因。基础设施故障和适配器故障应当被
删失，而不是伪装成算法失败。每一个标签都必须指向具体轨迹证据，不能只看终局报错字符串。

OCO 与部署机制正交。自由反馈系统、硬规则系统、软反馈系统和重放系统都可能在三个层次中的任意
一层失败。这样才能研究一种方法是否改变了错误分布，而不是先设计一套天然偏向某种架构的分类。

## 3. EnvSolve-Pro

### 3.1 设计原则

EnvSolve-Pro 只处理一个狭窄但关键的观测缺口：关于“这份交付程序能否在目标态运行”的证据，必须
在推理 session 结束前到达。方法保持 Agent 的操作空间开放，不加入包级修复规则、跨 case 经验、
模型外 compatibility frontier，也不让 harness 决定下一步操作。

### 3.2 Session 内目标态反例重放

EnvSolve-Pro 保持一个活跃 Agent session 和一个构建环境。Agent 可以用普通工具阅读仓库并改变
环境。当它提交完整程序 \(p_k\) 时，harness 创建目标初始状态，执行这份原样程序，再运行公开的
可执行目标。若失败，就把有执行依据的原始证据 \(z_k\) 返回同一个 session：

\[
z_k = \operatorname{Replay}(e_0, r, p_k).
\]

证据意味着什么、程序应该怎样修改，仍由 Agent 判断。下一份候选 \(p_{k+1}\) 可以采用完全不同的
策略。若重放通过，通过的同一份 \(p_k\) 才能交付。Official evaluation 与这个循环严格分离，只在
episode 结束后运行，绝不作为 session 内修复信号。

```text
启动一个 Agent session 和一个构建环境

在尚未得到通过重放的程序时：
    允许 Agent 自由检查或改变环境
    如果 Agent 提交完整部署程序 p：
        从目标初始状态执行 p，并运行公开目标
        如果执行通过：
            交付原样的 p
        把执行反例返回同一个活跃 session

如果 Agent 始终没有产生通过重放的程序，则返回失败
```

这个干预位于“形成候选”和“交付候选”的边界。它不能保证 Agent 一定能形成完整程序、为每个依赖
找到合法 provider，或在看到错误后选出有效操作。

### 3.3 与 OCO 的关系

观测接口包括普通执行反馈和目标态重放反馈。约束接口是 Agent 内部的判断 \(b_t\)，不是 harness
维护的 \(C_t\)。操作接口仍是 Agent 对命令和程序修改的自由选择。因此，OCO 可以解释闭环，却不
意味着当前实现真的包含三个符号化软件模块。

重放把一类失败提前了：遗漏的构建依赖、错误解释器、未复现的 shell 效果或工作目录假设，可以从
session 结束后的 Official 失败，变成 session 内可见的观测。这个观测能否进一步转化为成功修复，
取决于证据质量和 Agent 策略，需要由实验回答。

### 3.4 与其他反馈闭环的区别

普通交互 Agent 从累积构建环境中的命令获得反馈；EnvSolve-Pro 进一步要求反馈来自“目标初始状态
执行完整交付程序”。在本文观察的 Repo2Run 运行方式中，重放和回退用于保存或恢复构建进度；
EnvSolve-Pro 的干预对象则是最终需要交付的可迁移程序。因此，二者的区别不是有没有 loop，而是
可执行反馈的作用范围和出现时机。对于外部系统，我们以真实运行轨迹核验行为，不根据系统简介
推断细节。

## 4. 实验方法

### 4.1 证据单元与数据划分

失败研究的基本单位是一条完整的“方法--case”轨迹，包括模型消息、工具动作、改变状态的命令、
提交程序、重放结果和 Official 结果。已消费开发 case 可以用于定义 taxonomy 和筛选机制，但不能
支持未见测试或榜单结论。固定开发比较必须在看到 treatment 结果前选定；受保护 case 只用于估计
选定方法的泛化能力。

### 4.2 对比机制

我们把部署机制与模型 backbone 分开：

- 在一个活跃 session 中进行自由反馈搜索；
- 用编码的硬约束拒绝或改写行为；
- 用软的可执行证据提示 Agent，但不限制操作空间；
- 重放或恢复机制，并明确报告它重放的是哪一层状态；
- EnvSolve-Pro 在活跃 session 内执行完整程序的目标态重放。

同 backbone 的配对实验用于识别机制的因果作用。Repo2Run、原生 coding Agent 和 EnvBench baseline
属于端到端系统比较，因此必须报告模型、工具、重放和评测接口，不能假装成单变量消融。

### 4.3 评价指标

主要指标是 Official Pass@1。对失败轨迹，用 OCO 归因和终止阶段解释路径在哪里断裂。部署完整性
单独审计，因为“只满足指标的最小环境”和“功能完整的运行环境”可能得到相同 Official 分数。
资源指标按 case 报告，并重点比较共同成功子集；不能把单个离群 case 导致的总量下降推广成普遍
效率提升。

## 5. 开发期发现

### 5.1 失败原因不等于部署范式

当前 consumed-Dev census 从固定的 209 个 case 中得到 16 条非成功轨迹，其中 13 条有证据支持的
最早算法原因：观测层 6 条、约束层 5 条、操作层 2 条。另有 3 条间歇性包索引事件仍属于基础设施
未知，不计入分母。这是开发阶段的单人初始标注，不代表总体错误分布。

这些案例说明，终局报错类型不足以解释失败。多份程序看起来像“安装失败”，真正原因却是 checkout
权限或隔离构建事实直到 Agent 停止后才出现。另一些轨迹中，硬边界拒绝了后来能够通过 Official 的
程序；这属于方法施加了错误约束，而不是 Agent 做了有害操作。

### 5.2 重放忠实性与修复

在 3 个用于检查重放语义的已消费 case 上，最终通过重放认证的程序均通过 Official，其中 2 个触发
了预期修复闭环。一个 case 的重放暴露了遗漏的 Git ownership 操作；另一个依次暴露不可用依赖
版本、缺失的 ownership 处理和遗漏的测试依赖，同一个 session 根据每次反例修改了完整程序。由于
这些 case 按历史重放问题选取且没有配对 control，它们只能证明机制行为，不能估计预期成功率。

一个 outcome-independent 的 8 组开发期配对汇总比较了连续自由 Agent 与增加目标态重放后的同接口
Agent，Official 结果分别为 6/8 和 7/8；其中 1 组 treatment 单独通过，1 组共同失败。7 个形成最终
候选的 treatment episode 中，重放与 Official 全部一致，并出现 2 次基于反馈的修复。精确配对检验
不显著，因此这些证据支持机制忠实性和因果激活，但不能支持成功率提升结论。

### 5.3 候选形成是独立瓶颈

在固定的 4 组强 baseline bad-case 开发 batch 上，自由搜索与 EnvSolve-Pro 都通过 2/4。两组共同
失败里，Agent 都用完请求上限却没有形成完整候选，因此重放从未被触发。完整程序重放可以认证或
修复一个候选，却无法帮助探索过程变成候选。候选形成必须作为独立阶段测量。

### 5.4 更精细的残余状态没有提高成功率

一个三组配对实验在同样的闭环中加入了模型外 live compatibility frontier。Frontier 本身有效，
Agent 也确实使用了它，而且报告的残余 obligation 经常减少；但 control 和 treatment 都只通过 1/3，
没有任何 Official 不一致对。在一组共同失败中，treatment 清楚展示了依赖进度，却仍未找到可满足的
provider，也没有形成可交付程序。因此，我们只把 frontier 保留为诊断工具。残余数下降不能替代
终局成功。

这些实验共同暴露了“信息到行动”的缺口：系统可以观测到真实的残余条件，却仍可能无法推断可满足
要求、选择有效操作，或把探索过程整理成可迁移程序。EnvSolve-Pro 解决了其中一个观测缺口，但并不
声称已经解决所有转换。

## 6. 局限性

现有结果都是开发期证据，尚不能建立未见 case 上的提升、SOTA 或普遍效率结论。错误分布需要独立
复标后才能成为可靠统计。当前方法只有在 Agent 提交完整程序后才会激活，因此没有解决候选形成。
EnvBench Official 还允许功能完整性不同的部署路径得到相同分数，所以完整性必须单列。最后，外部
系统的反馈语义需要在匹配模型与预算的可复现实验中确认。

## 7. 结论

项目自动部署之所以困难，是因为兼容状态被隐藏、会随操作变化，并且只能通过执行逐步暴露。OCO
把观测、约束推理和操作失败分开，却不预设 harness 架构。EnvSolve-Pro 检验一个有意保持最小的
算法主张：当提出程序的 Agent 仍可行动时，从目标初始状态执行完整交付物，并把失败作为可执行反例
返回。开发轨迹表明，这能把一部分终局错误变成可行动证据；受控负结果同时说明，诊断变得更精细
并不等于部署变得更成功。任何新增机制最终都必须由终局成功率裁决，而不是由中间状态看起来多么
整齐来裁决。
