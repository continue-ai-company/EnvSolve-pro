# EnvSolve-Pro：面向仓库部署的部分可观测状态化约束求解

## 摘要

复现一个源码仓库，需要发现其没有完整声明的运行时、依赖、构建和平台条件。Agent 无法直接看到这些
隐藏条件，只能通过仓库证据以及在全新环境中执行程序的结果进行部分观测。现有部署 Agent 通常把状态
隐含在不断增长的语言模型上下文中，因此可能优化方便的代理测试、遗忘尚未解决的失败，或把基础设施
故障误当成部署证据。

我们将仓库部署形式化为**部分可观测状态化约束求解**，并提出 EnvSolve-Pro。一个公开的可执行目标在
不泄露终局评测结果的前提下定义成功。观测层在同一个全新环境中执行候选程序和目标，保留证据来源，
并区分 Pass、Fail 与 Unknown。约束层把目标驱动的失败转化为可修正的义务，同时把不确定的仓库推断
保留为假设。操作层把这一状态交给强语言模型；模型仍自由生成完整部署程序，而不是从封闭动作集合中
选择。执行结果继续更新状态，只有目标通过且完整性有效的候选才能被认证。

我们将在仓库部署 benchmark 上与 Repo2Run、原生编程 Agent 和同模型 Agent loop 比较。受控 baseline
获得相同的公开目标，从而区分目标可见性、显式状态和迭代约束修复的贡献。主指标是 Official Pass@1；
资源消耗只作为效率指标，而不是成功的硬阈值。

## 1. 问题

给定仓库 `R`、初始未知的环境状态 `z` 和公开可执行目标 `G`，Agent 需要生成部署程序 `P`，使得

```text
G(Execute(P, R, z)) = Pass。
```

Agent 不能直接检查 `z`。在第 `t` 轮，它在全新环境中运行候选 `P_t` 并得到观测 `o_t`，其中包括命令
结果、目标诊断和基础设施信号。每次观测只揭示部分相关状态：不同原因可能产生相似症状，有些失败只
暴露第一个被违反的条件，网络或模型服务故障也可能不提供有效的任务证据。因此，Agent 必须在多次
尝试之间持续修正其信念和义务。

可执行目标属于任务规范，而不是终局 evaluator。它包含版本化程序、报告 schema 和内容摘要。在线
solver 可以执行它，但永远看不到官方 benchmark 结果。这个边界既允许基于证据修复，也避免利用隐藏
标签调参。

研究目标是部署成功。时间、token 和环境数量是用于公平比较的实验控制，不是问题定义。

## 2. EnvSolve-Pro

### 2.1 观测层：发生了什么？

对每个候选，观测层记录所使用的仓库证据、完整部署程序、环境 identity、执行结果、目标报告和
effect audit，并给出三种目标状态：

- **Pass：** 目标程序完成执行，且报告满足声明的 schema。
- **Fail：** 目标程序完成执行，并返回具体的未满足条件。
- **Unknown：** 候选或目标无法被可靠评估，例如必要工具或网络操作失败。

Unknown 永远不会被转换为任务失败或成功。每轮使用全新环境，防止前一轮没有记录的状态变化偷偷影响
后一轮。目标报告还声明其 findings 是完整快照还是部分证据：只有同一作用域的完整快照才能用
“本轮未再出现”证明旧条件已经解除。

### 2.2 约束层：现在还有什么未满足？

约束层维护版本化状态 `S_t`，其中包含当前义务、已确认事实、不确定假设及其证据来源。目标失败是
权威义务：在同一目标的后续执行证明它已满足之前，它必须保持 active。仓库声明和模型解释可以说明或
细化义务，但不能删除可执行目标给出的证据。

状态转移由证据驱动且可撤销。新观测可以增加义务、细化 scope、把重复症状连接到共同原因、解除
义务，或令其继续未解决。部分观测只能增加或细化状态；完整的同作用域快照才可以逐项解除旧义务。
这个结构针对 raw-history Agent 的两个常见问题：在长轨迹中丢失决定性条件，以及把某条消息没有再次
出现误认为条件已经消失。

约束状态是模型的外部认知工具，而不是 Python 或 Linux 的完整符号模型。它的最小形式只是保留来源的
当前目标义务。因果压缩和额外语义推断只有在帮助解决问题、且不压制可执行证据时才有价值。

每个 active 义务还会定向路由最可能解释它的有界只读仓库证据：报告中的精确源码位置，以及缺失
subject 在仓库内的相关出现位置。这样可以把不透明症状转化为有依据的局部上下文，同时不让约束层
变成无边界的搜索与执行 Agent。

### 2.3 操作层：怎样改变环境？

操作层向强语言模型提供公开目标、当前约束状态和必要的原始证据。它还把当前最好的、完整执行且通过
完整性检查的候选保留为有执行证据支持的锚点。模型输出新的自包含部署程序，可以自由修改锚点，但应
保留仍与当前证据一致的设置。这样可以防止针对新暴露条件的修复，悄悄遗忘早期候选已经满足的条件。

EnvSolve-Pro 不把模型限制在预定义的包安装、运行时切换或构建动作中；封闭 operator 集既会限制未来
更强模型，也无法覆盖陌生仓库。

系统在隔离环境中执行该程序，随后立即在同一 shell 和环境中执行可执行目标。目标报告回到观测层，
形成闭环：

```text
观测 -> 更新约束 -> 生成操作 -> 执行目标 -> 再观测。
```

安全与完整性检查只约束哪些状态可以被修改，并确认观测到的 effect 确实来自当前候选；它们不规定
解决方案。只有目标状态为 Pass 且执行 effect 通过检查时，候选才被认证。

## 3. 三项贡献

1. **问题定义：** 将仓库部署形式化为带公开可执行目标的部分可观测状态化约束求解，分离在线证据与
   隐藏的终局评测。
2. **方法：** 提出兼容强模型的三层求解器，保留权威目标观测，维护可修正约束状态，并保持开放操作
   空间。
3. **评测：** 建立同目标受控协议，区分目标可见性与状态化修复的贡献，并通过外部部署 Agent、最终
   成功率和失败后恢复能力进行验证。

## 4. 实验设计

### 研究问题

- **RQ1：** EnvSolve-Pro 是否比 Repo2Run、原生编程 Agent 和同模型 Agent loop 获得更高的 Official
  Pass@1？
- **RQ2：** 公开目标、显式约束状态和可执行反馈驱动的状态更新分别带来多少贡献？
- **RQ3：** 方法能否提高首次部署失败后的修复率，并跨仓库、模型和执行平台保持效果？

### 对比方法

主要受控实验保持模型、工具、公开目标、终局 evaluator 边界和实验限制一致：

1. 不使用可执行目标的 free-form Agent loop；
2. 使用相同目标、但没有结构化状态的 goal-aware free-form Agent loop；
3. 具有观测、约束和操作三层的 EnvSolve-Pro。

Repo2Run 和原生编程 Agent 作为外部系统 baseline；冻结的 EnvSolve v1 作为历史结构化 baseline。核心
消融依次移除目标状态持久化、finding 定向仓库证据、保留候选锚点和 Fail/Unknown 区分。

### 协议与指标

开发、qualification 和最终评测按 repository identity 隔离。算法修改只使用已经完成的开发轨迹；
qualification 与 test 仓库在对应版本冻结前保持隐藏。每个终局候选都从干净环境重新评测，官方结果
永远不进入在线修复 loop。

主指标是 Official Pass@1。次指标包括首次成功率、以首次失败为条件的修复成功率、成功所需尝试数、
clean replay 和 Unknown 比例。Token、模型请求、候选环境、命令数和 wall-clock 用于描述效率与
success-resource trade-off。网络与 provider 事故作为被删失的基础设施结果报告，不计为算法失败。
逻辑模型调用与 provider transport attempt 分开报告。

对于 EnvBench Python，公开目标是 bootstrap 成功并且 `reportMissingImports` 为零；官方实现仍然只在
终局运行。所有 goal-aware 受控方法获得同一目标契约。最终结果表只会在代码、prompt、目标契约、
split identity 和分析规则全部冻结后生成。

### 当前开发证据

冻结的 5-case 开发资格实验尚未证明成功率提升。两个双方都完成且通过完整性检查的配对，在显式状态和
raw history 下都通过；显式状态表现出更低搜索负担，但样本太小、provider 时间方差过大，不能据此
声明效率收益。更重要的是，该批次暴露了两个通用瓶颈：很小的已验证修复仍会重复重放昂贵安装前缀；
symlink 可以制造合成 import alias，满足表面目标。我们因此先加固完整性边界，再把“从不可变的已验证
环境前缀分支”作为操作层机制进行检验；所有最终程序仍必须从全新环境完整重放。
