# EnvSolve-Pro 操作相关性合同 v1

状态：在实现之前、选择下一批开发仓库之前冻结设计。

## 动机

后置条件持久化实验能够保留正确的未解决 finding，却不能保证下一步操作在因果上
相关。已经消耗的 OpenQASM 轨迹中，不同方法在没有新证据时反复尝试等价的构建
路径。因此下一版只修改操作层。OpenQASM 只用于定义通用失败类型，不能用于选择
包、命令、路径或阈值。

## 合同

模型仍可输出任意完整、累积式 Bash 部署程序，不需要从预定义的包、运行时或构建
动作集合中选择。模型需要同时输出：

1. `target_finding_ids`：本次新修复针对的、当前仍活跃的可执行目标 finding；
2. `precondition_evidence_ids`：已经展示给模型、用于证明操作可行性的证据 ID；
3. `expected_resolved_finding_ids`：预计被消除的非空目标子集；
4. `operation_family`：用开放字符串描述本次修复的工具、机制和对象。

第一次目标观测之前，用一个合成 goal target 表示初始部署。family 描述本轮新引入
的修复，而不是从历史候选保留的累积式部署前缀。

## 机器检查

出现以下情况时，策略在分配容器之前拒绝候选：

- target 当前并不活跃；
- 预计消除的 finding 不属于 target；
- 引用的前提证据没有展示给模型；
- 已经获得可执行反馈后，候选没有引用执行、仓库或保留候选证据；
- 完整脚本此前已经得到确定性的目标失败；或者
- 同一个失败 operation family 再次处理重叠目标，却没有引用上次尝试未使用的新
  证据。

这些检查验证相关性和证据来源，不宣称能够理解任意 Shell 程序的完整语义。
operation family 由模型声明，因此可审计但不能抵抗恶意规避；完整脚本去重则由
harness 自己计算。论文必须明确这一限制。

## 进展证书

对于每个实际执行的合同，下一轮模型输入会记录：

- 执行前活跃 finding 集合；
- 预计消除集合；
- 执行后观测到的活跃集合；
- 预计 finding 中实际消失和仍然活跃的部分；
- 新出现的 finding；以及
- delta 是确定、未知、符合预期还是不符合预期。

只有同一目标的完整快照才能通过“未再次出现”消除 finding。报告缺失或不完整时
结果为 `unknown`，不能制造虚假进展。可执行目标通过时，合成的初始 target 才算
被消除。

## 冻结反例

合成测试必须拒绝：

1. 不存在的 target ID；
2. 不存在的 evidence ID；
3. 不属于 target 的预期消除 finding；
4. 已经确定失败的相同完整脚本；
5. 没有新增引用证据的同 family 重试。

合成测试必须允许：

1. 基于公开仓库 profile 的首次开放式部署；
2. 指向当前 finding 并引用对应 verification 的修复；
3. 引用新增执行反馈后的同 family 重试；
4. 不同的开放 operation family；以及
5. 不完整反馈之后的 `unknown` 进展结果。

## 验证规则

实现先通过合成测试和已消耗轨迹回放。只有代码、prompt、解析器、进展分析和 method
映射全部冻结后，才能打开通过元数据选择、仓库互斥的新 Dev batch。主对比为
`envsolve-pro-operation-contract` 与冻结的 fresh
`envsolve-pro-goal-contract-evidence-anchor`。Official Pass 是主指标；合同有效率、
失败后恢复率、重复抑制和进展校准是机制指标。Token 和时间只作为结果报告，不作为
成功的硬阈值。
