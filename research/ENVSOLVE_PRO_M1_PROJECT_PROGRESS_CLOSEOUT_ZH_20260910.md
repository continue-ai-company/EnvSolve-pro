# EnvSolve-Pro M1 项目进度筛查

日期：2026-09-10

机器可读证据：`experiments/analyses/envsolve_pro_m1_project_progress_closeout_20260910.json` 1.1 版。简短纠正文档见 `research/ENVSOLVE_PRO_M1_EVIDENCE_CORRECTION_ZH_20260910.md`。

## 问题与方案

M1 筛查一份很小的显式项目进度状态 `P`，能否改善后续部署：

1. `R0`：重放最近成功程序，只有失败后才调用新 Agent。
2. `R1`：继承完整 Agent session，并且每次都要求继续改进。
3. `P`：先重放；失败后，把程序、条件、状态变化和风险的紧凑记录交给新 Agent。

固定样本包含 4 个 consumed/Dev 项目。每个项目运行同 Python 的 `D1` 和一个预先声明、仓库支持的相邻 Python 版本 `D2`。三组统一使用 `gpt-5.6-sol`、`xhigh`、相同 public goal、Spark 目标环境和 episode 结束后的 Official 验证。没有使用 protected 数据，也没有替换项目。

## Official 原始结果

| 方案 | Pass | Nonpass | 缺失 |
|---|---:|---:|---:|
| `P` | 8 | 0 | 0 |
| `R0` | 6 | 2 | 0 |
| `R1` | 7 | 1 | 0 |

后续审计不能改写原始 Official 分数。R0 的 position-10 D1、position-22 D2，以及 R1 的 position-22 D2 都是原始 nonpass。R1 的 position-23 D2 虽然 run audit 无效，仍是原始 pass。

机制归因层面，P 和 R0 的 8 个格子都审计有效，R1 为 6/8。position 22 中 P 使用系统 Python 加 venv，R0/R1 保留 conda 并遇到 HTTP 000。这里无法分离顺序执行的时间变化和部署路径选择，所以 P 更好的原始表格尚不能证明显式状态带来可靠性增益。

## 模型用量

| `P` | 3,881,243 | 3,578,240 | 303,003 | 26,059 |

独立统计单位是项目（`n=4`）。P 比 R0 多用 6.6% 总 input 和 12.6% output，但少用 14.0% uncached input，因此是权衡，不是全面占优。P 比 R1 少用 58.5% input，但 R1 同时改变了触发策略：它每次重放后都调用模型，P/R0 可以跳过。本结果只能否定当前“总是调用”的 R1 策略。

每个项目的 token 和无效工程尝试都保留在机器可读记录中。两次误触发后中断的 Agent 分别消耗了 317.2 秒、717.8 秒可观测 wall time，以及 6、12 条容器命令；其 token 无法恢复，不能悄悄按零计算。

## 缺失检验

当前只是顺序复用/修复筛查，不是原计划中完整的累计进度实验。我们有 4 份 v1 种子和 24 份 v2/v3 状态文件，但没有在同一个固定 Q 上、不更新状态地比较 D0/D1/D2 版本。另外三个 R1 v3 文件没有正确把 D2 保存为当前条件。

因此，本轮尚未证明新版本的修复能否减少下一次探索，并抵消首次部署、更新和验证成本；也没有证明显式状态无用或 R0 已经最优。

## 裁决

**当前 P 不晋级，M1 等待阶段评审。** R0 只是一个强而简单的对照。R1 的结果只否定“总是调用模型的完整历史改进”作为默认策略。

最小补充实验只使用同一批 4 个项目和已有提交程序：在每个固定 D2 上，交错重复重放 P/R0 准确的更新前 v2 程序和更新后程序；不调用模型、不更新状态。主要指标是重复重放成功率，已有更新 token 和时间单独报告，用于判断能否摊薄成本。目前没有启动补充实验、M2 扩展或 protected 验证。
