# EnvSolve-Pro：将项目部署建模为部分可观测的状态化约束求解

## 摘要

复现一个软件项目，不只是生成一段看起来合理的安装脚本。部署 Agent 必须从不完整的执行反馈中推断不可直接观测的兼容状态，协调语言运行时、软件包、原生库、源码布局和生成产物之间相互作用的要求，最后把构建过程中得到的成功状态转化为能够从干净初始环境重新执行的程序。即使是具有长上下文和强推理能力的 coding Agent，也经常在这些状态转换中的某一步失败。

本文将项目部署形式化为**部分可观测的状态化约束求解**，并把推理闭环分解为三个接口：观测、约束和操作。观测层把执行结果转化为有依据的状态事实；约束层维护这些事实所蕴含的当前未满足条件与冲突；操作层允许 Agent 自由改变环境，同时把目标初始状态上的干净重放失败作为反例返回同一个活跃 session。这样的分解既保留强 Agent 的操作自由，也减少它反复从原始长轨迹中重建环境状态的负担。

我们在 EnvBench 上评估 EnvSolve-Pro，以 Official Pass@1 为首要指标。实验包括基于真实轨迹的因果失败分析、同 backbone 对照、Repo2Run 与 coding Agent 的原生系统对比，以及受保护评测。最终结果句和具体的约束更新 treatment 将在方法选择完成后的论文版本中给出。

## 1. 引言

项目部署是检验 AI 能否在真实软件世界中可靠推进任务的一类紧凑问题。Agent 得到一个固定 revision 的仓库，需要构建可执行所需工具的环境。它可能要选择解释器、恢复历史依赖版本、编译原生扩展、暴露生成代码、初始化子模块，或协调平台相关依赖。每次操作都会改变环境，但没有任何一条命令能够展示完整状态。

这暴露了命令级自由试错的局限。长轨迹会记录 Agent 输入了什么、Shell 返回了什么，却不会自动回答三个问题：

1. 当前环境的哪些事实已经真正成立？
2. 哪些要求仍然有效、彼此冲突，或者已经被反例推翻？
3. 下一步应该怎样改变状态，最终状态又能否从头复现？

更强的模型会减少局部推理错误，却不会消除上述结构。强 Agent 可以识别 import error 并提出候选软件包，但后续操作可能切换了解释器，使先前的安装失效；也可能在构建容器里得到成功状态，却没有把关键操作写入最终脚本。相反，僵硬的规则系统虽然能保持一致性，也可能阻止强模型发现合法解。因此，关键并不是用规则替代推理，而是在不压缩操作空间的前提下，让模型获得有执行依据的状态和约束信息。

我们用“观测--约束--操作”（OCO）闭环研究这个问题。这三层是推理接口，而不是三个软件模块。执行产生与特定环境状态绑定的观测；观测更新 case-local 的约束状态；Agent 结合当前约束和相关原始证据选择操作。当 Agent 给出部署程序后，系统从目标初始状态执行它；任何重放反例都会返回同一个活跃 session，并进入下一轮推理。

本文包含三项贡献：

1. **问题与分析贡献。** 我们将项目部署形式化为部分可观测的状态化约束求解，并提出有轨迹证据的 OCO 失败分析，用于定位最早产生决定性影响的推理转换。
2. **方法贡献。** 我们提出一个最小闭环部署方法，结合连续 Agent session、case-local 约束状态、开放环境操作和目标状态重放。最终论文只会纳入在受控实验中提高终局成功率的约束更新机制。
3. **实证贡献。** 我们设计同模型因果对照，并与 EnvBench Agent、Repo2Run、Codex 和旧硬约束 EnvSolve 做原生系统比较。Official Pass@1 是主指标；时间、Token、内存、存储和部署质量是次指标。

## 2. 问题定义

### 2.1 部署任务

一个任务实例写作

\[
x = (r, c, e_0, V),
\]

其中，\(r\) 是仓库，\(c\) 是精确 revision，\(e_0\) 是目标初始环境，\(V\) 是可执行成功条件。Agent 与可变的构建环境交互，最终返回部署程序 \(P\)。

只有当 \(P\) 从全新的 \((r@c, e_0)\) 出发产生被 evaluator 接受的终态 \(s^*\) 时，任务才算成功：

\[
s^* = \operatorname{Replay}(P, r@c, e_0), \qquad V(s^*) = 1.
\]

构建环境里的局部 Pass 如果无法被程序复现，就不算成功；中间错误数量下降也不等于成功。

### 2.2 部分可观测

用 \(s_t\) 表示第 \(t\) 步后的真实环境状态。它包含活跃解释器与 Shell、已安装 distribution、系统库、文件系统产物、源码根目录、生成文件、环境变量和解析器状态。Agent 无法直接看到 \(s_t\)，只能得到观测

\[
o_t \sim \mathcal{O}(s_t, q_t),
\]

其中 \(q_t\) 是 Shell 命令、包管理器查询、import 尝试、构建或公开 verifier 等探针。每个探针只揭示部分状态，有时还会改变状态。没有输出不代表某个条件不存在，旧证据也未必仍能描述当前环境。

这种部分可观测性来自真实部署本身。依赖声明可能不完整；软件包名和 import 名并不总是一致；distribution 可以安装成功却不包含所需符号；生成 provider 可能只有在构建后才出现。平台与网络行为还会引入更多隐藏变量。

### 2.3 状态化约束

EnvSolve-Pro 用一组有证据支持的约束表示当前判断：

\[
C_t = \{c_t^1, \ldots, c_t^m\}.
\]

每个约束描述目标部署必须满足的条件，并保留状态与证据。例如：某模块是否存在于活跃解释器中、运行时与二进制包是否兼容、生成源码树是否可用，以及某个 Shell 状态能否进入最终程序。

更新规则

\[
C_t = U(C_{t-1}, o_t)
\]

可以激活、满足、推翻约束，或把它标为不确定。更新必须保留足够的 provenance，才能区分当前事实和历史观测。约束状态是给 Agent 的建议，不替代原始证据，也不是操作空间上的硬限制。

### 2.4 操作与终局程序

Agent 在每一步选择操作

\[
a_t \sim \pi(h_t, C_t, o_t), \qquad s_{t+1} = T(s_t, a_t),
\]

其中 \(h_t\) 是连续 session 历史。操作既可以检查状态，也可以改变任何与部署有关的状态。EnvSolve-Pro 不假设固定包管理器，也不使用封闭动作集合。

系统最终输出的不是构建容器，而是可重放程序 \(P\)。因此，重放失败是一条描述“构建状态与交付程序之间差距”的一等观测，而不是事后的格式错误。

### 2.5 成功与预算

主结果是终局 Official Pass@1。即使中间达到目标，只要没有返回可重放程序，该 run 仍然记为失败。模型请求、Token、墙钟时间、峰值内存、网络流量和存储属于实验条件和次级指标，不属于问题定义；只有在不降低成功率时才优化它们。

## 3. EnvSolve-Pro

### 3.1 方法概览

EnvSolve-Pro 在整个 episode 中保持同一个 Agent session 和同一个可变构建环境。其闭环为：

\[
\text{执行} \rightarrow \text{观测} \rightarrow \text{更新约束}
\rightarrow \text{选择操作} \rightarrow \text{重放候选程序}.
\]

该闭环把证据、判断和动作分开。同一条 Shell 输出可能支持不同约束，同一约束也可能存在多个合法操作解。

### 3.2 观测层：现在知道什么？

观测接口把执行反馈转成状态证据。一条观测包含：

- 产生它的操作或探针；
- 对应的环境身份；
- 退出状态和有界原始输出；
- 可执行 verifier 能提供的结构化 finding；
- 执行不完整或基础设施不稳定时的不确定性。

观测是追加式证据，但不会因为曾经出现就永久成为真值。后续切换解释器或源码树会使其状态解释过时，同时原始记录仍被保留用于分析。

### 3.3 约束层：现在还必须满足什么？

约束接口把证据映射成当前部署义务，集中回答四个问题：

1. 哪些条件仍未满足？
2. 哪些旧条件已经满足或失效？
3. 哪些要求在当前运行时和平台下相互冲突？
4. 哪些判断仍然不确定，需要新的探针？

约束是 case-local 且有证据依据的。它可以压缩反复出现的诊断，但 Agent 能查看对应原始证据，并推翻错误解释。目标是在不缩小强模型合法解空间的前提下，减少从长轨迹重建状态的成本。

### 3.4 操作层：怎样改变状态？

操作接口保持开放。Agent 可以执行任意非交互部署命令，包括安装软件包、创建环境、源码构建、检查元数据和生成代码。约束状态帮助选择动作，却不会自行选择软件包，也不会直接阻止操作。

这使 EnvSolve-Pro 区别于硬约束部署系统。安全和 evaluator 隔离是所有方法共享的实验基础设施，不被包装为部署策略贡献。

### 3.5 连续 Session 与反例重放

构建反馈和重放反例都进入同一个活跃 session。这样可以保留局部推理连续性：Agent 知道为什么选择某个解释器、失败安装改变了什么，以及当前分支由哪个残余要求触发。

当 Agent 形成完整程序 \(P\) 后，EnvSolve-Pro 在干净目标环境执行它。若重放失败，失败结果成为新的观测 \(o_{t+1}^{R}\)，相应的构建--交付矛盾进入 \(C_{t+1}\)，Agent 在同一 session 内继续修复。若重放通过，则把同一个精确程序提交给 Official evaluator。

### 3.6 最小算法

```text
输入：仓库 r@c、目标环境 e0、公开 verifier V
初始化活跃 Agent 历史 h0、构建状态 s0、约束 C0 = 空集

循环：
    从活跃环境获得有执行依据的证据 ot
    Ct <- update(Ct-1, ot)，并保留证据来源
    at <- agent(h_t, Ct, 相关原始证据)
    在活跃构建环境中执行 at

    如果 Agent 给出完整部署程序 P：
        y <- 从全新的 (r@c, e0) 重放 P
        如果 y 通过 V：
            返回这份被精确重放的 P
        否则：
            把 y 作为重放反例返回同一个 session
直到 episode 终止
```

最终采用哪一种约束更新实现，只由受控设计实验中的终局成功决定。中间 frontier 更平滑、诊断更清楚或轨迹更结构化，都不足以让一个机制进入核心算法。

### 3.7 与 Baseline 的关系

自由 ReAct 提供原始执行历史，但不维护显式的当前约束状态，也不要求目标状态重放。Repo2Run 将反馈搜索与 checkpoint、回退结合，重点是恢复构建进度。原生 coding Agent 具备强通用策略和连续交互，但本身不定义由 benchmark 控制的约束与重放语义。旧 EnvSolve 使用硬约束拒绝或改写行为。EnvSolve-Pro 保持软约束和自由操作策略，并通过可执行重放反例闭合推理循环。

## 4. 实验设置

### 4.1 Benchmark 与数据划分

我们使用 EnvBench 的 Python 部分。重建后的 benchmark 包含 329 个仓库 revision，其中官方训练侧 229 个，Official Test 侧 100 个。开发轨迹只用于 taxonomy 发现和机制选择。受保护的 20-case canary 与 100-case Official Test 不参与最终方法设计。所有暴露都按仓库 identity 记录，已消费开发 case 不能支持未见仓库结论。

### 4.2 对比系统

对比包括 EnvBench FreeAgent、Repo2Run、原生 Codex 部署 Agent、旧硬约束 EnvSolve，以及同 backbone 自由 Agent。同 backbone 对照用于识别 OCO 闭环的因果作用；原生系统比较用于衡量端到端能力，但不会把不同模型栈伪装成受控消融。

### 4.3 指标

首要指标是配对 Official Pass@1。生成未完成、未形成候选程序或程序不可重放都记为失败。次级指标包括模型请求、输入与输出 Token、墙钟时间、峰值内存、网络与存储、干净重放次数和部署质量标签。成本使用稳定的资源单位报告，不设置美元硬阈值。

### 4.4 统计设计

机制假设只从已消费轨迹中产生。每个 treatment 首先与同 case、模型、seed、镜像、目标和 evaluator 的 control 匹配比较。晋级必须有终局成功证据；中间错误下降只能作为机制证据。被选中的方法随后进入受保护 identity，且不再进行 case-specific 修改。

## 6. 分析

### 6.1 OCO 失败迁移

对每条非成功轨迹，只在证据支持反事实归因时标注一个最早决定性层：观测失败表示关键事实不可得或未被获得；约束失败表示事实已出现，却没有被保留或正确协调；操作失败表示相关要求已经活跃，但所选状态转换或交付程序没有满足它。基础设施事故单独报告。

### 6.2 设计实验结论

设计实验用终局结果区分算法进展与更好的诊断。分析围绕三个问题：证据是否到达活跃 session，证据是否改变当前约束判断，以及这种改变是否产生可重放的 Official success。只改善前两步的 variant 会被保留为测量工具，而不会进入核心方法。

### 6.3 模型能力

我们检验随着底层模型增强，显式状态约束是否仍然有用。假设并不是“强模型无法自己推断约束”，而是即使局部推理很强，绑定执行状态的证据仍能减少过时状态推理和构建--交付丢失。因此，强弱 backbone 在相同方法定义下分别评估。

## 7. 相关工作

EnvSolve-Pro 连接了软件工程 Agent、自动环境构建、依赖求解和部分可观测交互规划。与一次性脚本生成不同，它把不断变化的环境视为推理状态的一部分；与经典依赖求解器不同，它必须从仓库证据和任意执行中推断约束；与不受限制的 coding Agent 交互不同，它把目标状态可复现性显式纳入反馈闭环。

## 8. 局限性与结论

EnvBench 主要测量 import provider 的可执行可用性，不能完整覆盖语义运行正确性、测试充分性或生产部署质量。静态 import 成功也可能对应完整性和资源差异很大的环境。因此，我们将 Official success 与部署质量标签分开报告。发布容器平台上的结果也不能直接证明对所有操作系统和加速器都可迁移。

项目部署不应被描述为自由命令生成，而是证据、判断和动作共同演化的部分可观测状态化约束求解。EnvSolve-Pro 将这一视角实现为最小闭环：有依据的观测、证据支持的约束、自由环境操作，以及返回同一 Agent session 的干净重放反例。受保护评测将检验这一闭环能否同时提高强模型和较弱模型的终局部署成功率。
