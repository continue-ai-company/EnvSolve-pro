# EnvSolve-Pro Operation-Relevance Qualification Casebook v1

Status: pre-closure diagnostic record. These repositories are consumed development
evidence, not held-out or final-test evidence.

## Evidence Boundary

The frozen five-repository paired qualification compares
`envsolve-pro-operation-contract` with the frozen fresh
`envsolve-pro-goal-contract-evidence-anchor` control. The original analysis, corrected
measurement analysis, infrastructure amendment, schedules, and artifact hashes are
preserved under `experiments/validations/pro_operation_relevance_contract_v1_*`.

Only Django has a complete pair before infrastructure closure. Trax is provider-censored
in both conditions. UER-py has a method-induced treatment timeout and a
provider-capacity-censored control. Tortoise ORM and libEnsemble received no valid model
response. No aggregate effectiveness claim is admissible yet.

## Case 3: UER-py

The treatment is a primary non-pass under the frozen protocol. Its first candidate
installed the declared requirements and exposed 11 missing modules. The second candidate
targeted all 11 and added optional README dependencies, including TensorFlow, but exceeded
the 1,200-second candidate command timeout before producing a complete goal observation.
The descriptive state remains `execution_timeout_unknown`; it is not eligible for an
infrastructure retry.

The control used a broad first action and reduced the target to the single persistent
finding `tensorflow.keras.backend`. It then tried Python 3.11 with TensorFlow 2.15 and
Python 3.10 with TensorFlow 2.14. Both complete snapshots retained the same finding. A
fourth model request was rejected by provider credit capacity, so the control outcome is
externally censored and scheduled for exact retry.

This trajectory separates constraint visibility from operation viability. Both methods
could retain the precise unresolved import. Neither available operation established why
an installed TensorFlow distribution remained invisible to the static goal, and the
treatment's evidence contract did not prevent an expensive, nonterminal dependency
expansion.

## Provisional Cross-Case Diagnosis

1. The contract can encode a correct low-dimensional repair, but Django shows no success
   gain and higher resource use.
2. Exact finding IDs plus a fixed projection window create avoidable interface friction
   on high-fanout failures. Grouped or queryable targets are a candidate redesign, not a
   result established by one censored case.
3. Evidence provenance does not by itself establish operation feasibility. UER-py
   suggests the missing diagnostic is often about runtime/package-layout semantics rather
   than the identity of the unresolved import.
4. The preregistered duplicate-family suppression mechanism was never exercised.
   V1 therefore has no suppression-based qualification signal so far.

No algorithm change is allowed until the frozen infrastructure closure completes. Final
interpretation must use Official Pass@1, count method-induced terminal failure as a
non-pass, censor only external failures, and report the original and corrected
measurement views.

### UER-py Dependency-Closure Replay

A preregistered infrastructure replay selected UER-py because its consumed episode had
the largest persisted download lower bound. The unchanged candidate command resolved six
declared requirements to 35 ARM64 wheels and a 2.896 GB cache snapshot, dominated by
PyTorch and CUDA 13. Direct and initially empty-cache lifecycles both exceeded the
2400-second wrapper limit during `docker run --rm`, although their verification markers
were present. A third fresh client installed and imported the identical closure in 93.74
seconds while DevPI was process-level offline. It exited normally, produced zero remote
cache reads, and left the snapshot unchanged.

This case has two distinct uses. First, it proves that repeated dependency acquisition
is a major infrastructure confound and that an isolated seeded cache can remove it.
Second, it sharpens the Operation-layer hypothesis: an operation that accepts the
unconstrained latest PyTorch closure on ARM64 can spend roughly 2.9 GB and the whole
candidate window before testing goal relevance. The future solver should observe and
reason about platform fit and bounded dependency closure, but this replay does not
itself justify a new rule or an algorithm-effect claim.
