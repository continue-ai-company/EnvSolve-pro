# EnvSolve-Pro M1 证据纠正

日期：2026-09-10

本文纠正第一版 M1 收口。修正后的机器可读记录是 `experiments/analyses/envsolve_pro_m1_project_progress_closeout_20260910.json` 1.1 版。

## 正确证据

episode 结束后的 EnvBench Official 原始结果如下：

| 方案 | Pass | Nonpass | 缺失 |
|---|---:|---:|---:|
| `P` | 8 | 0 | 0 |
| `R0` | 6 | 2 | 0 |
| `R1` | 7 | 1 | 0 |

第一版把 position 22 的 R0 和 R1 写成了“未知”，这是错误的。两次原始 Official 都返回 `exit_code=1, issues_count=0`。position 23 的 R1 返回 `exit_code=0, issues_count=0`；即使其 run audit 无效，这个原始 Pass 仍应计入。

原始分数、协议有效性和因果归因必须分开。position 22 中，P 从 conda 改为系统 Python 加 venv 后通过，R0/R1 保留 conda 并遇到 HTTP 000。由于三组顺序执行，这可能来自部署路径、随时间变化的网络，或两者共同作用，不能自动算成外部 censor，也不能当成榜单结果。

## 结论边界

P/R1 的 token 比较有混杂：R1 每次都继承完整历史并要求继续改进；P 和 R0 在重放通过后会跳过模型。因此，58.5% 的 input 降幅只说明“总是调用模型的完整历史策略”昂贵，不能否定失败后才复用完整历史的自适应方案。

P 与 R0 是成本权衡，不是谁全面占优：P 总 input 多 6.6%、output 多 12.6%，但 uncached input 少 14.0%。独立样本是 4 个项目，不是 8 个条件。

M1 还没有完成原计划中的累计进度检验。虽然 v1/v2/v3 状态文件存在，但没有执行“状态版本 × 固定 Q”的探针矩阵；另外三个 R1 v3 文件没有正确记录 D2。当前证据只能称为顺序复用/修复筛查。

## 科学裁决

当前 P 不晋级。这表示其机制增益尚未建立，不表示显式状态无用，也不表示 R0 已经最优。最强替代解释是：成功的可执行程序已经吸收了大部分可复用收益；position 22 的差异则来自部署路径选择和执行时点。

最小后续实验只使用这 4 个项目和已有产物：在同一个固定 D2 条件上，交错重复重放每组准确的更新前 v2 程序和更新后提交程序；全程不调用模型、不更新状态。先报告重复成功率，再单独报告此前已经付出的更新成本。它直接回答“修复后是否留下了可复用进度，以及这份进度能否摊薄构建成本”。

目前没有启动补充实验。M2 和 protected 数据仍未获授权。
