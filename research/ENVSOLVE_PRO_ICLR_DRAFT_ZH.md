# EnvSolve-Pro：面向仓库部署的部分可观测状态化约束求解

状态：ICLR 工作论文稿，2026-08-18

## 摘要

仓库部署通常被视为命令生成：Agent 阅读仓库、执行命令，最后返回安装脚本。这个视角忽略了核心难点：
兼容性状态只能被部分观测，操作会持续改变状态，而交互工作区中的成功不一定能从干净 checkout 中重现。
我们把仓库部署定义为**部分可观测状态化约束求解**。

我们首先记录可审计部署轨迹，并把失败组织为三个因果层：观测层、约束层和操作层。已有证据表明，主要
瓶颈不只是缺少依赖知识，而是提交程序真正需要工作的状态被过晚或不完整地观测。我们据此提出
EnvSolve-Pro：在一个连续 session 中保留自由 Agent，按固定节奏执行完整且绑定环境身份的观测，跟踪兼容
义务如何变化，并通过干净重放认证完整程序。harness 只提供证据，不替 Agent 选择包、阻断操作或恢复
checkpoint。

我们使用同模型配对实验、外部部署 baseline 和独立强 Agent 前沿进行评估。Official Pass@1 是主指标；
机制激活、失败层迁移和成功条件下的资源使用解释增益来源。一个预注册的可选观测 pilot 从 2/4 提高到
3/4，但因为一条 treatment 轨迹完全没有使用观测工具而未通过机制资格。这一负结果直接导向当前研究所
评估的确定性观测节奏。

## 1. 问题定义

给定仓库修订 \(x\)、基础环境 \(E_0\) 和公开目标 \(G\)，Agent 与构建环境交互并返回部署程序 \(P\)。
最终交付的环境是

\[
E_P = R(P, E_0),
\]

其中 \(R\) 从干净状态执行完整程序。部署成功要求

\[
G(E_P)=1 \land I(x,P,E_P)=1,
\]

其中 \(I\) 是所有方法共享的评估完整性条件，覆盖仓库身份、目标身份和产物来源。

### 1.1 为什么是部分可观测

Agent 无法预先读出完整兼容性状态。依赖求解、构建隔离、Python 身份、原生库、ABI、硬件、网络和
进程局部状态，只会在特定操作后显现。更重要的是，交互构建环境与干净重放环境不是同一个状态：失败命令
可能留下部分副作用，shell 配置可能只在当前会话存在，最终脚本也可能漏掉交互阶段发生过的操作。因此，
执行既是改变环境的动作，也是获取信息的手段。

### 1.2 预算是实验条件

时间和请求上限用于保证实验可比与安全，但不属于问题定义。成功优先于省钱。token、墙钟时间、网络、
磁盘和内存是在相同上限下测量的结果，而不是强制优化目标。

## 2. 三层失败框架

我们标注最早产生决定性影响的原因，而不是最后一条错误字符串。

### 2.1 观测层：发生了什么？

必要事实缺失、绑定到错误环境身份、发现得太晚，或把局部结果误当完整状态，都属于观测失败。例如，测试
所用 Python 与提交程序不同，或者直到交互 session 结束后才在干净环境发现依赖冲突。

### 2.2 约束层：现在必须满足什么？

证据没有转成正确兼容义务、冲突义务未被识别，或已解决义务仍被当成活跃问题，都属于约束失败。义务可
涉及运行时版本、包版本区间、构建依赖、系统库、ABI、平台和状态传播。

### 2.3 操作层：怎样改变状态？

操作无法解除当前义务、顺序错误，或无法被提交程序重现，都属于操作失败。harness 若压制强 Agent 的
合法动作，也会制造操作层失败。

三个层次存在因果关系：没有观测到的事实无法形成约束，没有形成的约束也无法被操作准确修复。

## 3. EnvSolve-Pro

### 3.1 公共评估底座

所有受控 arm 共享底座 \(E\)：隔离 Official evaluator，固定仓库和目标身份，绑定提交程序精确 hash，
并保存可审计 artifact。E 让证据可信，但不推断兼容性、不选择动作，因此不是算法 treatment。

### 3.2 定时观测

EnvSolve-Pro 在三个时机执行完整公开目标观测：

1. 第一次模型请求前；
2. 每完成 \(K=16\) 次 shell 操作后；
3. 干净重放前，且环境在上次观测后发生过变化时。

每次观测记录可执行文件身份、环境路径、相关已安装分发、完整 finding 集合和有界原始证据。该节奏只从
历史已消费轨迹确定一次，不根据新实验结果调参。

### 3.3 状态化约束前沿

对于相邻的完整 finding 集合 \(Q_{t-1}\) 和 \(Q_t\)，harness 返回

\[
\text{resolved}_t = Q_{t-1} \setminus Q_t, \qquad
\text{introduced}_t = Q_t \setminus Q_{t-1}.
\]

观测和增量被追加到活跃 session 的证据前沿。证据来源单调积累，但推断出的兼容状态可以改善、退化或
转向。这个前沿只提供指导，不安装包，也不限制 Agent 的操作空间。

### 3.4 自由操作与干净重放

同一个 Agent session 自由选择 shell 操作并编辑完整部署程序。候选只有在独立干净环境中执行完全相同的
程序后才能获得认证。重放失败及其绑定环境身份的观测返回活跃 session 继续修复。Official evaluator
只在 episode 结束后调用，永远不进入修复循环。

```text
Q <- 观测干净构建状态
把 Q 交给同一个连续 Agent session

while 尚无重放认证程序且安全上限未耗尽:
    Agent 自由检查、操作并编辑 P
    每 K 次 shell 操作:
        Q' <- 观测当前构建状态
        把 delta(Q, Q') 和原始证据返回同一个 session
        Q <- Q'
    Agent 请求重放时:
        若构建状态已变化，先观测
        result <- 从干净状态执行精确 P
        把重放证据返回同一个 session

只返回经过重放认证的程序 hash
```

该方法不包含包规则库、物理 checkpoint、跨 case 记忆、学习策略或 harness 自修改。

## 4. 三个贡献

1. **失败分类与观测系统。** 我们提供跨系统可审计轨迹，以及观测层、约束层、操作层 taxonomy，用于识别
   环境部署失败最早的决定性原因。
2. **最小部署算法。** 我们提出 EnvSolve-Pro，把确定性的环境身份绑定观测、状态化证据前沿、同 session
   自由操作和干净重放组合起来，同时不编码包选择，也不阻断强 Agent。
3. **受控实证。** 我们比较同模型因果增益、强弱模型表现、Official 成功率、失败分布迁移和资源 Pareto
   行为，并与自由搜索、硬约束、重放式方法、Repo2Run、EnvBench 和原生 coding Agent 对照。

## 5. 实验设计

### 5.1 失败研究

EnvBench FreeAgent、Repo2Run、原生 Codex、旧硬约束 EnvSolve 和 EnvSolve-Pro 中全部科研有效的已消费
轨迹进入回顾性 taxonomy discovery；基础设施失败单独删失。每个失败 episode 标一个关联证据的最早
决定性主标签。按系统和类别分层确定性抽取 20% 样本独立复标，报告原始一致性、Cohen's kappa 和最终
裁决。该语料只支持 taxonomy 与失败画像，不支持系统成功率比较。

### 5.2 机制资格实验

当前 qualification 在四个此前已消费仓库上比较“同 backbone 自由搜索 + 干净重放”control 与
EnvSolve-Pro，每个 arm 两次重复，并平衡顺序，共 16 个 episode。每个 treatment episode 必须遵守冻结
观测节奏；至少 75% 的计划观测必须完整；harness 必须施加零操作约束并创建零 checkpoint。

晋级要求 Official Pass 数不下降、最多一个 treatment 独占失败，并且至少出现一个 treatment 独占成功
或一个预注册的成功条件效率信号。这个小实验只判断机制是否合格，不估计最终效果大小。

### 5.3 确认性实验与 baseline

机制合格前不打开冻结 Dev identity。随后在 Canary 和 protected evaluation 前冻结算法、prompt、tool
schema、taxonomy、model/provider binding 和分析代码。受控比较保持模型和公共底座一致。系统级 baseline
包括 EnvBench FreeAgent、Repo2Run、冻结的旧 EnvSolve，以及作为独立前沿参考的原生 Codex。强弱
backbone 实验检验 harness 是增强模型能力，而不是替代模型能力。

主指标是 Official Pass@1。次级机制指标包括调度符合率、义务集合迁移、候选就绪到重放时延、重放修复
以及配对失败层迁移。资源既报告无条件结果，也报告成功条件下结果。Official 成功与更广义部署完整性是
两个独立评价轴。

## 6. 当前证据与证伪条件

14 条已消费强 Agent 轨迹包含 898 次 shell 操作和 50 次自然全局兼容检查，平均间隔 17.96 次操作。在
36 个可比较状态迁移中，36.1% 停滞或退化。这说明强 Agent 会主动检查全局状态，但节奏不稳定，有时会在
局部看似合理的工作上持续很久。

一个预注册的八 episode pilot 测试了可选 compatibility-ledger 工具。八条有效轨迹全部通过有效性检查。
treatment 的 Official 通过数为 3/4，重放 control 为 2/4，有一个 treatment 独占成功且没有独占失败。
在该独占成功中，完整 findings 从 16 个义务降到 0，随后修复了一个重放冲突；其配对 control 很晚才找到
正确环境，并在没有重放的情况下耗尽 120 次请求。

但机器最终判定为 `negative-mechanism-not-qualified`：一条成功 treatment 轨迹从未调用工具。在双方均
成功的配对上，treatment 相对 control 的请求数、交互步骤、token 和证书时间中位数比值分别为 1.30、
1.28、1.46 和 1.11。结果说明完整的环境身份绑定观测至少能解决一个 bad case，但否定了“由 Agent 自愿
调用工具”是一种稳定机制。

如果确定性调度仍不能稳定产生完整观测、降低 Official 成功率、制造 treatment 独占失败，或没有可复现
的修复或效率信号，EnvSolve-Pro 的主张就应被证伪或收窄，而不是继续加入 case-specific 规则。

## 7. 范围与局限

EnvBench Official 主要衡量 missing-import 兼容性，不能证明完整应用行为。公共完整性底座可以拒绝无效
测量 artifact，但不能证明部署算法有效。第一篇论文研究固定 harness，不包含跨 case 学习、harness 自动
搜索或 Agent RL。
